# Practical work — T1

T1 adds /practice and a persistent, private three-session API-app exercise. It supplements an existing course and is also available without a course or accepted plan. Learners construct fixed promise, fetch and DOM scaffolds from code choices, predict fixed success/error traces, save partial drafts, explicitly submit and inspect deterministic feedback. No arbitrary learner code runs, no endpoint is fetched and no provider call is needed. This adopted prototype approach is an implementation choice, not a validated assessment or a founder-approved change to the product strategy.

## What the rubric observes

The immutable api-mini-app-v1 catalog uses guided-api-rubric-v1. Each of three sessions has four criteria, tagged with the shared js.promises, web.fetch-api or web.dom skill ID and a narrowly worded scope. Known correct scaffold choices are met; observed incorrect choices need review; missing choices are inconclusive. An overall result is inconclusive if any criterion is missing, while specific observed gaps remain visible. With twelve observed choices, any incorrect choice yields needs_review; all twelve correct yields meets_guided_rubric.

These are guided construction and trace observations, not an independently built app. The rubric does not assess arbitrary program correctness, code quality, authorship, deployed behavior, comprehensive mastery or career qualification. The learner may submit free-form code instead; that mode has no guided choices and its result is entirely inconclusive. Supplementary code and reflection never substitute for guided observations. Both remain inert private text, escaped by React. Switching to free-form mode asks before clearing unsaved guided choices. Feedback is generated by fixed server-only rules; no AI-grade or invented confidence score is shown.

The original scaffolds and rubric use documented JavaScript/Web API semantics. References checked 14 October 2026: [MDN promises](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Using_promises), [MDN fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch) and [MDN textContent](https://developer.mozilla.org/en-US/docs/Web/API/Node/textContent). Fetch HTTP-status handling, asynchronous JSON parsing and textContent's text behavior are particularly relevant. These links support technical semantics; they do not validate the rubric as a learning measurement instrument.

## Versions and state

Public exercise content and private grading keys have content hash 55969b48184f293a06e4b77705bd528ea52c0abe294183231918f3a6c1bb0d63. Private keys are imported only by server-only scoring code. The database catalog stores public content/hash, not keys. Every attempt retains the public content, rubric version and hash so history cannot be silently reinterpreted by later content. Any future exercise change needs a new catalog/rubric version and retained scoring support for older drafts. Unsupported versions preserve saved work and reject mutation.

An attempt is draft or submitted, with a positive revision. Start resumes the one existing draft for this catalog, or creates a new attempt tied to the current goal and the then-accepted proposal, if any. A later goal/plan change does not rewrite that provenance or block returning to the original draft. Submission is immutable; a new attempt allows another try. T1 never completes the accepted plan, advances a checkpoint, creates assessed evidence or promotes a skill. T2 adds a separate explicit progress recording action; see [PRACTICAL_PROGRESS.md](PRACTICAL_PROGRESS.md). Submission itself still changes no evidence. Passing a scaffold must not later be interpreted as broad mastery.

## API and ownership

| Method | Route | Behavior |
|---|---|---|
| GET | /api/practice?page={n} | Catalog, latest 20 owned attempts, active draft and next-page cursor |
| POST | /api/practice | {requestId}; start/resume owned draft |
| GET | /api/practice/{id} | Owned retained content, work and feedback; opaque 404 for foreign IDs |
| PUT | /api/practice/{id} | {requestId, expectedRevision, operation: save/submit, input} |

Input contains exactly mode, choices, code and reflection. There are at most twelve known slot/option IDs, code at most 12,000 characters and reflection at most 2,000. Open work cannot contain guided choices. Mutation bodies are limited to 64 KiB; start bodies use the existing smaller limit. Routes derive identity from cookie authentication, require trusted-origin JSON for mutations and return private/no-store responses. Server-owned RLS reads precede construction of the authorized privileged writer. Private attempts and receipts allow owner SELECT only; catalog SELECT is authenticated. Only service_role executes the start/save/submit RPCs. No client may forge feedback or insert assessed evidence.

Mutations share the learner advisory lock with Passport, courses, diagnostics and plans. Request fingerprints cover operation, attempt, expected revision and input. Exact receipts return before current revision/status checks, including a start or draft save retried after submission. Changed input with the same ID returns 409. New stale saves/submissions and foreign attempts fail atomically; a submitted attempt cannot be edited. The database independently validates known choices, feedback shape, criterion IDs/shared skills/scopes/observed choices, inconclusive handling and overall outcome. The server-only scorer owns correctness; service_role is trusted and is never exposed to clients. Created/submitted events are audit activity, not skill findings.

The client freezes an uncertain payload and request ID, protects unsaved work on same-tab navigation/sign-out/unload, and rereads current state after receipts. Expired sessions can be renewed in a new tab. Conflicts preserve local entries and offer an explicit comparison; using the saved version asks before replacement. Newer submitted work cannot be overwritten. Browser crashes and full offline persistence are not guaranteed. Questions/code are not stored in localStorage or sent to OpenAI by this feature. Account deletion cascades private attempts/receipts; pilot export/delete controls remain later work.

## Verification and follow-up

Unit checks cover complete/incorrect/partial/open work, unsupported choices, bounded schemas, private key separation and version stability. Real Postgres checks cover immutable outcomes, exact retries, concurrent starts, invalid feedback, changed goals, role grants, cross-user isolation, account cleanup and unchanged evidence/plan state. Browser journeys cover returning and beginner paths, saving between sessions, fresh sign-in, explicit submission, escaped free-form work, conflicts, lost committed responses, expired sessions and mobile layout. Final build, CI and hosted acceptance results are recorded in the T1 PR.

T2 now records only supported, scoped guided evidence and a proposed follow-up on its feature branch. Calibration with independent learner work and rubric review remains a pilot requirement; a scaffold-only pass must retain its limitations.
